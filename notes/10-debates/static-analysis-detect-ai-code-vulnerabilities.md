## Question

The question is whether off-the-shelf static analysis tools (SAST) can reliably detect the vulnerabilities in code generated by LLMs, or in the samples of secure-code benchmarks. The sources contest it between 2021 and 2026 for CodeQL, Semgrep, Bandit, Cppcheck, Clang Static Analyzer, FlawFinder, Snyk Code and SonarQube. Each source judges static analysis against its own reference: Z3 satisfiability witnesses, an LLM judge applying metamorphic relations, executed exploits, runtime errors, manual review of alerts. "Reliably" therefore covers different measures: the share of vulnerabilities found by another method that the tools also flag, the stability of tool verdicts across equivalent code, and the precision of the alerts the tools raise.

## Positions

### Static analysis misses much of it

The Broken by Default paper (Blain and Noiseux) holds that industry static tools miss nearly all of the vulnerabilities its formal method proves. On its 50-prompt v1 corpus of 250 artifacts, six tools (Semgrep, Bandit, Cppcheck, Clang Static Analyzer, FlawFinder and CodeQL) together flagged 19 artifacts (7.6%) and 2 of the 90 findings proven by Z3 satisfiability witnesses, missing **97.8%** of them (p. 5, p. 6). CodeQL security-extended flagged none of the 68 C and 22 Python Z3-proven artifacts, and Cppcheck and Clang SA flagged none of 87 C artifacts (p. 5, p. 6). The authors call this "a structural gap, not a configuration issue": detecting overflow in allocation arithmetic needs arithmetic reasoning under modular semantics, which pattern and taint-based analysis lack (p. 5, p. 6). The reference is the authors' own COBALT engine, which combines pattern extraction, Z3 encoding and witness extraction (p. 3), and the authors are its developers (p. 1). The paper reports no false-positive rate for COBALT and validates 7 findings at runtime, 6 of which produced faults (p. 3, p. 4). The text also refers to "80 confirmed C vulnerabilities" for an experiment run on 87 C artifacts (p. 5).

The metamorphic-testing study by Peng, Wang and Zhu finds that four open SAST tools flag about half as many snippets as its own method. On 3,700 snippets from five open models on LLMSecEval prompts, an LLM judge (Claude Sonnet 4.6) applying nine security-oriented metamorphic relations finds 68.8% of snippets violating at least one, while CodeQL, Bandit, Semgrep and Flawfinder together flag **34.2%** (p. 3). Separately, CodeQL flags 3 snippets (0.1%), Bandit 45, Semgrep 90 and Flawfinder 1,130 (p. 4). No SAST tool detects any authentication-bypass violation, and the tools catch 44 of 651 hard-coded-credential violations (p. 3). The judge reasons about code statically and does not execute it (p. 2). The paper reports a 36-snippet pilot review with "high accuracy" but gives no figure, so it reports no measured precision or recall for the judge on which the comparison rests (p. 5).

CWEval (Peng et al. 2025) argues that static-analysis-based security evaluation is unstable. It reports that only 562 of the 1,916 vulnerable samples in CyberSecEval are still flagged by that benchmark's associated static analyser (p. 2). It also shows CodeQL's incomplete-URL-sanitisation rule giving false negatives and a false positive on semantically similar redirect implementations (p. 2). The paper's response is to measure security with dynamic, outcome-driven oracles and to "not rely on any static analyzer" (p. 5). Its evidence on static analysis is a reproduction count on one benchmark's samples and a worked example on one rule (p. 2).

BaxBench (Vero et al.) compares Snyk Code with its executed exploits on the 237 correct programs generated by o1. Snyk missed 64 vulnerable programs that the exploits compromised (p. 8). Of 25 programs Snyk flagged that the exploits did not trigger, 16 (6.75%) were false positives, 2 concerned rate limits, and 7 (2.95%) were correct additional flags across 3 CWEs (p. 8). The paper states that these results "signify the unsuitability of SAST tools for benchmarking" (p. 8). Its own reference is bounded: exploits may miss vulnerabilities, so it treats its measured sec_pass as an upper bound on true security (p. 24). The paper also used Snyk Code in developing its exploits (p. 4).

Chong et al. qualify the position from a different reference. GPT-4o's C solutions to 202 LeetCode problems were run on the online judge and compiled with AddressSanitizer, and the paper reports that the Clang static analyzer missed 8 of the 12 runtime errors (p. 7). The authors conclude that static analysis alone is insufficient, since some runtime errors escaped it (p. 11). The errors are runtime failures on LeetCode tasks, such as buffer overflow and signed integer overflow, rather than findings identified as vulnerabilities (p. 7, p. 8). The same paper uses Clang as its main security scorer and reports a negligibly low false-positive rate in its manual validation (p. 6).

Pearce et al. qualify it from inside a study that relies on CodeQL. CodeQL configured for the single targeted CWE was the main detector, with manual marking where it could not be used and for Verilog (p. 4, p. 5). Among their limitations, the authors acknowledge that CodeQL cannot reason about memory buffer sizes, that some CWEs need information beyond the file, and that it may have marked some safe code vulnerable (p. 13).

### Static analysis is a usable safeguard

The Sonar study by Sabra, Schmitt and Tyler argues for static analysis as a safeguard for generated code. It scans Java code from five LLMs on 4,442 tasks with SonarQube's default ruleset of about 550 rules (p. 5), and reports bugs, vulnerabilities and code smells from every model (p. 9). It concludes that prompt engineering is not a sufficient safeguard on its own and that static analysis and expert human review are essential (p. 16). It adds that static analysis should be complemented by Software Composition Analysis for deprecated APIs and vulnerable dependencies, which analysis of the generated code alone does not address (p. 12, p. 21). The authors are affiliated with Sonar, the company behind SonarQube, the tool the study uses (p. 1). SonarQube is the study's only detector (p. 5), and the paper reports no measure of what the tool misses or of its false positives.

RealSec-bench (Wang et al.) qualifies the position. It uses CodeQL as its security oracle but does not take its alerts at face value: an alert counts only if a panel of voter LLMs and a final-judge LLM do not reclassify it as a false positive (p. 5). On 89 manually reviewed alerts, CodeQL alone has **44.9%** precision, and voters plus judge raise precision to 81.7% at 98.0% recall (p. 6). These figures are computed over alerts that CodeQL raised (p. 6). The authors list dependence on SAST tools and their false positives as a threat to internal validity, and state that the adjudication remains limited by LLM accuracy and falls short of manual expert annotation (p. 9).

## Why they differ

The sources judge static analysis against different references. Blain uses Z3 witnesses from its own COBALT engine, which the authors develop, with 7 findings checked at runtime (p. 1, p. 3, p. 4). Peng (2026) uses an LLM judge whose precision and recall it does not report (p. 5). CWEval counts how many of a benchmark's labelled samples its analyser still flags, and gives a worked example on one CodeQL rule (p. 2). BaxBench uses executed exploits, which it treats as giving an upper bound on security (p. 24). Chong uses runtime errors on LeetCode solutions, not identified vulnerabilities (p. 7). Pearce reports CodeQL's limits as limitations of its own study (p. 13). The two sources on the other side measure something else. Sabra reports what SonarQube finds, without a measure of what it misses, and is published by the company that sells the tool (p. 1, p. 5). RealSec measures the precision of CodeQL's alerts and of their LLM adjudication, over the alerts CodeQL raised (p. 6). The code under analysis also differs: C and Python artifacts dominated by allocation and integer-arithmetic findings (Blain, p. 5, p. 6), Python and C snippets from LLMSecEval prompts (Peng 2026, p. 3), CyberSecEval samples (CWEval, p. 2), backend applications (BaxBench, p. 3), LeetCode C solutions (Chong, p. 7), Copilot completions (Pearce, p. 4), Java benchmark tasks (Sabra, p. 5) and functions in real Java repositories (RealSec, p. 1).
