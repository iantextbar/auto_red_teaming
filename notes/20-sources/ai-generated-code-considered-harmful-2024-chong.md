## Stated by the source

### What it is about

The paper compares the security and quality of C code generated by OpenAI's GPT-4o with human-written code for the same tasks: 202 LeetCode problems, 15 data structures and algorithms, and three cryptographic routines (p. 2, p. 4). It builds an evaluation framework, **EXACT**, that combines unit tests, fuzzing, the Clang static analyzer and complexity measures (p. 2). It pursues three research questions: whether an LLM generates insecure code, whether it is more or less secure than human code for the same task, and whether prompt engineering can improve it (p. 4). The audience is software-security researchers and practitioners adopting AI code generation.

### Argument

The paper opens from a gap between adoption and scrutiny. AI code assistants are spreading, productivity gains are reported, and the security of what they produce is, in the authors' words, under-studied and largely ignored by industry (p. 1). Three small motivating experiments set up the concern. GPT-4o is asked to fill in a buffer size and gets it wrong in many conditions, especially when the size requires calculation; it implements SHA-1 so that every hash is wrong though the code compiles; and it writes a graph allocator with no checks on the vertex count or on the `malloc` result (pp. 3–4).

The central comparison then follows. Functionality is first checked against LeetCode's online judge, unit tests and AFL fuzzing, and by test vectors for the cryptographic routines (pp. 5–6). The paper reports that GPT-4o fails more often on harder tasks and has silent failures, such as SHA-1, that only strict testing would catch (p. 7). The security comparison is run with Clang. GPT-4o code has more issues overall, concentrated in **malloc overflow**, which the authors attribute to the model assuming all inputs are valid (p. 7). Fuzzing shows more hangs and crashes in the LLM code (p. 7).

The quality argument turns on a reading of the complexity numbers. GPT-4o code has lower absolute cyclomatic complexity and fewer lines, but the paper argues this is an artifact of "bare-bones" code that omits input validation, collision checks and other **defensive programming**. Normalised complexity (complexity per line of code) is higher for GPT-4o, and the authors treat that as the more indicative measure (p. 8). A further concept is **code parroting**, where the model reproduces human-written code verbatim (2 of 18 files). The authors warn that this could propagate poisoned or malicious training data (pp. 7–8).

The last move tests the remedy. A feedback loop re-prompts GPT-4o to remove a named class of Clang-detected issue from 60 of its own LeetCode solutions, 30 with issues and 30 without. The loop reduces some issue counts but not to zero, increases array-index-out-of-bounds issues, and introduces new malloc overflows in files that had none (pp. 9–11). The authors conclude that the LLM cannot be relied on to consistently remove security issues even when told to, and that static analysis alone is insufficient since some runtime errors escaped it (p. 11). They conclude that LLM-generated code should be considered potentially harmful as long as it is prone to security risks (p. 13).

### Interlocutors

- Pearce et al. 2022 (Copilot security study): cited for the finding that 40% of 1,689 Copilot programs were vulnerable. Role: counterpoint-in-agreement, motivating evidence (p. 3).
- Perry et al. 2023 (user study on AI assistants): participants with an assistant wrote significantly less secure code. Role: foundation, aligned with the paper's findings (p. 12).
- Zhang et al. 2024 (Cybench) and Bhatt et al. 2023 (CyberSecEval): benchmarks the paper calls orthogonal to its purpose and says EXACT could incorporate. Role: related benchmarks (p. 12).
- McAleese et al. 2024 (CriticGPT) and the Copilot secondary-model work: automated LLM feedback to improve code. Role: target of critique; the study examines the security of systems that may contain such black-box components (p. 3).
- Schuster et al. 2021 and Yan et al. 2024 (poisoning and backdoors in code completion): support the danger the paper attaches to code parroting (p. 12).

### Methodology

Controlled comparative experiment on matched tasks. Each LLM task is prompted with the task description, plus the header file or function declarations of the human implementation so that signatures match (p. 5). Human code comes from public GitHub repositories (p. 5). Functionality is checked with LeetCode submissions, manually written CUnit tests (regular and edge cases), AFL fuzzing and cryptographic test vectors (p. 6). Security is scored with the Clang static analyzer's default and experimental checkers, and the authors report a negligibly low false-positive rate in their manual validation (p. 6). Quality is measured with SCC for cyclomatic complexity and lines of code (p. 6).

### Empirical base

- One model, GPT-4o, in C (p. 2, p. 13).
- 202 LeetCode problems from a GitHub solutions repository; 18 data-structure and algorithm files (the text says 15 algorithms and data structures plus three cryptographic algorithms) (p. 2, p. 4, p. 7).
- Human code from four GitHub repositories (TheAlgorithms/C, fragglet/c-algorithms, petewarden/c_hashmap, OpenBSD) (p. 5).
- Feedback loop on 60 GPT-4o LeetCode files (30 with issues, 30 without) (p. 9).
- Buffer-size experiment: 1000 trials per definition (p. 3).

### Findings

- On LeetCode, 87.6% of GPT-4o solutions passed the online checks; the failures were time limits, failed tests, runtime errors and compile errors (p. 7).
- All GPT-4o data structures and algorithms passed unit tests, while 3 of 15 human ones did not (p. 7).
- AFL fuzzing: 12 unique hangs for GPT-4o against 6 for human code, and 451 unique crashes against 364 (p. 9).
- GPT-4o's SHA-1 gave wrong hashes for all inputs; its MD5 and AES were correct (p. 7).
- Clang found 128 issues in GPT-4o code against 116 in human code (10.3% more), with malloc overflow 81 against 61 and memory leaks 8 against 16 (p. 7, p. 9).
- Normalised complexity is higher for GPT-4o; absolute complexity and lines of code are lower (p. 8, p. 10).
- Feedback loop on files with issues: 58 issues before, 44 after; on files with none: 0 before, 4 malloc overflows after (p. 11, p. 12).

### What the source offers

- A reusable pipeline (EXACT) pairing LLM output with human implementations of the same interface, combining static analysis, fuzzing, unit tests and complexity metrics; the authors say they will open-source it (p. 2).
- A buffer-size probe with per-condition success rates over 1000 trials (p. 5).
- A worked case where static analysis and the runtime checker disagree: 8 of 12 runtime errors were missed by Clang (p. 7).

### Stated gaps and limitations

The study uses a single model, GPT-4o, and the authors leave other LLMs (Llama3, Claude) to future work (p. 13). The tasks are small and independent, unlike large projects such as kernels or browsers (p. 13). The authors say the black-box nature of RL-based improvement means they cannot know whether security improved in deployed systems (p. 13). They also note that the memory-leak counts for human code are largely due to LeetCode problem statements saying the caller frees memory (p. 7).

### Key claims

- On the study's tasks, GPT-4o-generated C code had 10.3% more Clang-reported security issues than human-written code (128 against 116) (p. 7, p. 9).
- GPT-4o code had 32.8% more malloc overflow issues than human code, which the authors attribute to the model assuming all inputs are valid (p. 7).
- AFL fuzzing produced 23.9% more unique crashes in GPT-4o code than in human code on the data-structure and algorithm tasks (p. 7).
- GPT-4o's SHA-1 implementation gave incorrect hashes for every test input yet compiled, which the authors describe as a silent error (p. 7).
- GPT-4o's success at determining a buffer size in a prompt fell with calculation and with irrelevant context, e.g. from 99.3% to 31.2% when an irrelevant string-length calculation was present (p. 4).
- GPT-4o code has higher normalised complexity per line than human code, while its lower absolute complexity reflects less code and a lack of defensive programming (p. 8).
- In the feedback loop, GPT-4o reduced malloc overflow issues from 40 to 24 but did not remove them, and array-index-out-of-bounds issues rose from 15 to 18 (p. 10, p. 11).
- In the feedback loop, regenerated code introduced 4 new malloc overflow issues in files that had no such issues before (p. 10, p. 12).
- Static analysis alone missed 8 of the 12 LeetCode runtime errors in GPT-4o solutions (p. 7).
- The authors state that 2 of 18 data-structure and algorithm files were exact replicas of human code, which they call code parroting (p. 7, p. 8).

## Extracted facts

- Model and target: GPT-4o, which the paper says powers GitHub Copilot Enterprise; language C (p. 2).
- Buffer-size probe (Table 1, 1000 trials each): constant integer 99.3%; length of alphabet string 92.8%; pow(4, 2) 91.4%; 415 * 495 63.1%; 922 - 174.05 50.1%; pow(1,5) + 63.56 42.4%; alphabet with a missing letter 41.6%; constant with irrelevant string length 31.2%; 893 * 518.33 10.6%; 285.63 * 62.72 1.5%. In 0.08% of results the model emitted meaningless non-English characters in place of an int (pp. 3–5).
- LeetCode: 202 problems; 87.6% pass, 12.4% fail (p. 7). Table 2 lists 25 failed questions: 2 time limit exceeded, 12 runtime errors, 7 failed test cases, 4 compile errors (function definition with an invalid number of parameters) (p. 8). The text says runtime errors are 48% of failing solutions and that 9 (39.6%) failed tests or time limits (p. 7).
- LeetCode runs are compiled with AddressSanitizer; the error types include buffer overflow, signed integer overflow, array index out of bounds and heap-buffer-overflow (p. 7, p. 8).
- Human-written failures: 3 of 15 data-structure and algorithm files failed unit tests (doubly linked list with == on doubles; red-black tree with a missed return statement and null dereference); queue, doubly linked list and red-black tree could not be fuzzed and are N/A (p. 7).
- Fuzzing totals (Table 3): hangs GPT-4o 12, human 6; crashes GPT-4o 451, human 364. The text reports 50% more hangs and 23.9% more crashes for GPT-4o (p. 7, p. 9).
- Clang totals (Table 4, 220 files: 202 LeetCode, 18 data structures and algorithms): GPT-4o 128, human 116. Memory leak 8 vs 16; null pointer dereference 6 vs 8; malloc overflow 81 vs 61; array index out of bounds 16 vs 17; implicit conversion 4 vs 1 (p. 9). Malloc overflow is 63.3% of the issues across GPT-4o code (p. 10).
- Clang checkers: default, plus experimental Core, Security and Unix checkers (p. 6).
- Cyclomatic complexity (Table 5), mean: LeetCode 7.37 (GPT-4o) vs 8.10 (human); data structures and algorithms 25.7 vs 34.5. Mean complexity per line: LeetCode 0.33 vs 0.28; data structures and algorithms 0.21 vs 0.17 (p. 10). The introduction gives 1.19x (LeetCode) and 1.26x (algorithms) (p. 2).
- Lines of code (Table 6), mean: LeetCode 23.6 vs 29.6; data structures and algorithms 103.5 vs 192.1 (p. 10).
- Feedback loop: three loops, one per issue category (malloc overflow, array index out of bounds, null dereference); the 30 files with issues split 18, 10 and 2 (Table 7). Each loop adds an instruction to the original prompt not to have the named issue, with paired issue-free files (p. 9, p. 10, p. 11).
- Feedback loop results: files with issues, malloc overflow 40 to 24, array index 15 to 18, null dereference 3 to 2, total 58 to 44 (Table 8); files without issues, 0 to 4 in total (Table 9) (p. 11, p. 12).
- Line-length prompts, reported in the introduction only: asking for shorter lines gave 11.3% lower cyclomatic complexity per line and fixed 17.9% of Clang issues; asking for fewer lines gave 18.4% higher complexity per line and fixed 43.2% (p. 2).
- The authors report identifying 116 security issues in public GitHub repositories and disclosing them to the owners, and contacting OpenAI (p. 2).
- Funding: NSF grant CCF-2106710; OpenAI donated API credits (p. 13).
- Inconsistencies in the text: the introduction says 21 LeetCode tasks failed, 20 of them medium or hard (p. 2), while the 12.4% failure rate on 202 problems and Table 2 list 25 failing questions, 3 of them easy (p. 7, p. 8). The introduction gives 11.2% (LeetCode) and 7.1% (algorithms) more Clang issues (p. 2), and Section 5.2 gives 10.3% overall (p. 7). The text reports 50% more hangs, while Table 3 totals are 12 against 6 (p. 7, p. 9). The Section 5.2 count of 220 files (202 + 18) differs from the 15 data structures and algorithms plus three cryptographic algorithms named in the introduction and Section 4 (p. 2, p. 7). The line-length prompt results appear only in the introduction and not in the feedback-loop section (p. 2, p. 9).
