## Stated by the source

### What it is about

The paper reports a study of the security of code generated by seven production LLMs on 500 security-sensitive prompts (five CWE categories, 100 prompts each), 3,500 artifacts in all (p. 1, p. 2). Its stated contribution is methodological: using the Z3 SMT solver, through the authors' own COBALT pipeline, to establish that a flaw is exploitable rather than merely suspected (p. 1). It pursues six research questions: vulnerability rates, differences across models, whether Z3 witnesses become runtime exploits, the effect of security instructions, COBALT against industry static tools, and whether models can detect their own vulnerabilities (p. 2). The audience is developers and security engineers using AI coding assistants.

### Argument

The paper starts from the premise that earlier work on insecure LLM code relies on static pattern matching or manual inspection, which cannot "definitively establish exploitability" (p. 1). It proposes replacing that with formal verification: a vulnerability condition (for example the integer overflow of `n * sizeof(T)` in a `malloc` call) is encoded as a Z3 formula over bit-vectors, and when the solver returns satisfiable, the witness value is taken as the concrete exploit input (p. 3). Findings are sorted into **Z3 SAT** (proven), **PATTERN MATCH** (structural, no Z3 encoding yet) and clean (p. 3). Seven selected findings are then turned into proof-of-concept harnesses compiled with AddressSanitizer to answer the objection that pattern detection inflates counts (p. 3).

The first empirical move is the baseline. Across the seven models the mean vulnerability rate is **55.8%**, with 1,055 Z3-proven findings; GPT-4o is worst at 62.4% and Gemini 2.5 Flash best at 48.4%, and no model reaches grade C under the paper's own grading scale (p. 3, p. 4). Integer-arithmetic prompts fail most (87%), then memory allocation (67%), and the authors attribute both to a consistent failure to guard integer overflow in allocation arithmetic and in signed/unsigned conversions (p. 4). Six of seven PoCs produced runtime faults; the seventh (a Zip Slip) was blocked by Python 3.12 at runtime, so the pattern was present but not exploitable there (p. 4).

Three auxiliary experiments on the earlier 50-prompt corpus then address mitigations. First, a security-explicit system prompt lowers the mean rate only from 64.8% to 60.8%, with memory allocation essentially unchanged; the authors read this as security instructions not overriding low-level patterns learned from training data (p. 4, p. 6). Second, six industry tools (Semgrep, Bandit, Cppcheck, Clang Static Analyzer, FlawFinder, CodeQL) together flag 7.6% of artifacts and 2 of the 90 Z3-proven ones. The paper argues this is "a structural gap, not a configuration issue", because detecting the overflow needs arithmetic reasoning under modular semantics that pattern and taint-based analysis lack (p. 5, p. 6). Third, when each model reviews its own Z3-proven vulnerable code it flags it 78.7% of the time, which the authors call a **generation–review asymmetry**: the knowledge is present but not applied during generation (p. 5).

The conclusion is that AI coding assistants are "broken by default", that prompt-level mitigation is insufficient, and that Z3-based verification should be mandatory in any AI code review pipeline on memory-sensitive or security-critical targets (p. 7). The discussion adds a hypothesis that the failures reflect training data in which C code overwhelmingly lacks overflow guards (p. 6).

### Interlocutors

- Pearce et al. (2022), Copilot on 89 scenarios and 18 CWEs, 40% vulnerable: prior work whose pattern-based analysis lacks exploitability proofs (target of critique, p. 2).
- Tony et al. (2023), LLMSecEval, 150 prompts and 5 LLMs: prior benchmark of insecure generation (counterpoint, p. 2).
- Perry et al. (2023) and Sandoval et al. (2023): user studies in which assistant users wrote more vulnerabilities (counterpoint, p. 2).
- Meta CyberSecEval (2024) and SecurityEval (2022): adversarial-capability benchmark and a pattern-evaluated prompt set; the paper calls its own focus "orthogonal" to the first (counterpoint, p. 2).
- He and Vechev, SVEN (2023): steering toward secure output; the paper measures unsteered baseline generation instead (counterpoint, p. 2).

### Methodology

An empirical benchmark study with execution-based confirmation. Natural-language prompts are issued to seven models at temperature 0, and the code is analysed by the authors' COBALT engine, which combines regex/AST pattern extraction, Z3 encoding and witness extraction (p. 3). A small set of findings is validated by PoC harnesses under GCC AddressSanitizer and UBSan (p. 3). The ablation, tool comparison and self-review experiments run on the older 50-prompt corpus (p. 5).

### Empirical base

- Main corpus (v3): 500 prompts across MEM, INT, AUTH, CRYPTO and INP, seven models, 3,500 artifacts, queried in Q1–Q2 2026 (p. 2, p. 3).
- Auxiliary corpus (v1): 50 prompts, five models, 250 artifacts (p. 4, p. 5).
- Self-review: 89 valid Z3-proven artifacts (p. 5).
- Dataset released at a GitHub repository (p. 7).

### Findings

- Mean vulnerability rate of 55.8% across seven models; per-model range 48.4% to 62.4% (p. 3).
- Highest category rates: integer arithmetic 87%, memory allocation 67%; lowest: cryptography 25% (p. 4).
- 6 of 7 selected Z3 findings were confirmed as runtime faults; the seventh was blocked by Python 3.12 (p. 4).
- Security-explicit prompting reduced the v1 mean from 64.8% to 60.8% (p. 4, p. 5).
- Six industry tools combined caught 19 of 250 v1 artifacts and 2 of 90 Z3-proven ones; CodeQL caught 0 of 90 (p. 5, p. 6).
- Models flagged 70 of 89 of their own Z3-proven outputs when asked to review them (p. 5).

### What the source offers

- A labelled dataset of 3,500 generated artifacts with Z3 labels, plus prompt templates, scripts and PoC harnesses (p. 7).
- A worked operational definition of "proven" exploitability for integer overflow in allocation arithmetic: a Z3 bit-vector witness (p. 3).
- A per-tool comparison (Semgrep, Bandit, Cppcheck, Clang SA, FlawFinder, CodeQL) on generated code (p. 6).

### Stated gaps and limitations

The benchmark covers five CWE categories only, and other categories may behave differently (p. 7). All runs were at temperature 0, multi-turn and retrieval-augmented settings were not tested, and higher-capability model tiers were left out (p. 3, p. 7). The ablation was run on the 50-prompt corpus only, and the Llama increase may be within noise (p. 7). Per-model rates across the v1 and v3 tables are not directly comparable because the Claude model differs (p. 4).

### Key claims

- Across seven LLMs and 500 prompts, 55.8% of artifacts contained at least one COBALT-identified vulnerability, with 1,055 findings proven by Z3 satisfiability witnesses (p. 1, p. 3).
- On this prompt corpus no model reached better than grade D on the authors' scale; GPT-4o was worst at 62.4% and Gemini 2.5 Flash best at 48.4% (p. 3).
- Integer-arithmetic prompts produced the highest mean vulnerability rate (87%), followed by memory allocation (67%) (p. 4).
- Six of seven selected findings were confirmed by AddressSanitizer or equivalent runtime faults (p. 4).
- A security-explicit system prompt reduced the mean rate on the 50-prompt v1 corpus by only 4 points (64.8% to 60.8%), and memory-allocation vulnerabilities were essentially unchanged (p. 4).
- Six industry static tools together flagged 7.6% of v1 artifacts and missed 97.8% (88/90) of Z3-proven findings, which the authors attribute to a structural limitation (p. 5, p. 6).
- Models identified their own Z3-proven vulnerable code in review mode 78.7% of the time (70/89), which the authors read as a generation–review asymmetry (p. 5).
- The authors state that formal SMT verification is the only methodology that can establish ground-truth exploitability of the dominant vulnerability patterns (p. 1).

## Extracted facts

- Grading scale: A under 10%, B 10–29%, C 30–44%, D 45–59%, F 60% or more vulnerability rate (p. 3).
- Table 1 (500 prompts per model): GPT-4o 62.4% (F), Llama 4 Scout 60.6% (F), Llama 3.3 70B 58.4% (D), Mistral Large 57.8% (D), GPT-4.1 54.0% (D), Claude Haiku 4.5 49.2% (D), Gemini 2.5 Flash 48.4% (D); mean Z3-proven findings per model 150.7, mean CRITICAL 157.0, mean HIGH 90.1 (p. 3).
- Severity follows CVSS v3 base-score bands: CRITICAL at 9.0 or above, HIGH 7.0–8.9, MEDIUM 4.0–6.9 (p. 3).
- Table 2 mean rate by category: memory allocation (CWE-131/190) 67%, integer arithmetic (CWE-190/195) 87%, authentication (CWE-916) 44%, cryptography (CWE-327/330) 25%, input handling (CWE-89/22/78) 56% (p. 4).
- Models: gpt-4o, gpt-4.1, claude-haiku-4-5-20251001, gemini-2.5-flash, mistral-large-latest, llama-3.3-70b-versatile, llama-4-scout-17b-16e-instruct; temperature 0; system prompts asked for complete runnable code without commentary (p. 3).
- PoC table: MEM-01-A (Llama) and MEM-01-B (GPT-4o) heap-buffer-overflow, MEM-03 (Llama) alloc-size-too-big, MEM-06 (GPT-4o) out-of-bounds read, AUTH-03 (Llama) SHA-256 password recovered in 0.01 ms by precomputed lookup, INP-01 (Mistral) SQL injection with data exfiltration, INP-06 (GPT-4o) Zip Slip blocked by Python 3.12 (p. 4).
- Table 4 (v1, 50 prompts, base to secure): Llama 3.3 70B 68% to 70%, GPT-4o 66% to 58%, Gemini 2.5 Flash 60% to 60%, Claude 3.5 Sonnet 64% to 62%, Mistral Large 66% to 54%; mean 64.8% to 60.8% (p. 5).
- v1 tool comparison: COBALT flagged 162/250 (64.8%), of which 90 Z3 SAT (36.0%) and 72 PATTERN MATCH; Semgrep 16/250, Bandit 5/250, combined 19/250 (7.6%); on 87 C artifacts Cppcheck 0, Clang SA 0, FlawFinder 4 (strcat and rand only); CodeQL v2.25.1 security-extended 0/68 C and 0/22 Python Z3 SAT artifacts (p. 5, p. 6).
- Cppcheck was run with all checks enabled at exhaustive level; the paper states that only 113 of 592 checkers activate on standard C11 code (p. 5).
- Table 6 self-review: Mistral Large 17/17, Llama 3.3 70B 14/17, Gemini 2.5 Flash 14/18, Claude 3.5 Sonnet 13/19, GPT-4o 12/18; total 70/89 (78.7%), false-negative rate 21.3%; one artifact excluded after a Mistral API timeout (p. 5, p. 6).
- The paper's comparison "models generate them at 55.8% by default" sets a v3 seven-model rate against a v1 self-review on five models including Claude 3.5 Sonnet, not Claude Haiku 4.5 (p. 1, p. 4, p. 6).
- The same 64.8% figure appears as COBALT's v1 detection rate (162/250) and as the v1 baseline vulnerability rate (p. 5, p. 7).
- The text says cppcheck and Clang SA detected zero of "80 confirmed C vulnerabilities" while the same experiment is run on 87 C artifacts (p. 5).
- Absence bearing on a claim: the paper calls Z3 verification ground truth, but reports no false-positive rate for COBALT and validates only 7 findings at runtime; the PATTERN MATCH tier is counted in the 55.8% headline rate without Z3 confirmation (p. 3, p. 4). The authors are the developers of COBALT, the tool that scores best in the comparison (p. 1).

## Quotes

- "Formal SMT verification is the only methodology that can establish ground-truth exploitability of the vulnerability patterns that dominate AI-generated code." (p. 1)
- "Models were queried via their production APIs at temperature 0 (deterministic mode)." (p. 2)
