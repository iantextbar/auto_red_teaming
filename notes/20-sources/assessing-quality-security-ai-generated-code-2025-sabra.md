## Stated by the source

### What it is about

The paper, written by authors affiliated with Sonar (the company behind SonarQube, the tool used), measures the quality and security of Java code generated by five LLMs for 4,442 benchmark tasks (p. 1, p. 5). It asks four questions: the typical quality profile of LLM Java code (RQ1), the most common issue categories and severities (RQ2), how well static analysis can detect these defects (RQ3), and whether better functional performance goes with better code quality and security (RQ4) (p. 4). It is aimed at organisations deploying AI in software development, and it states that its goal is not to rank models but to show shared weaknesses (p. 1).

### Argument

The paper starts from the premise that discussion of LLM coding has centred on functional correctness (Pass@1 on unit tests), which leaves the broader quality and security of the output under-examined, while AI assistants are widely adopted and developers may trust insecure output (p. 3). It posits that LLM code is not production-ready without verification, so functional metrics alone are insufficient (p. 4).

It then runs the same prompts at temperature zero through five models and analyses every file with the SonarQube default Java ruleset (about 550 rules) (p. 5). The first move is descriptive: the models differ in volume, complexity and comment density (p. 7), but the mix of issue types is strikingly similar, about 90-93% code smells, 5-8% bugs and about 2% vulnerabilities (p. 9). The paper reads this similarity as a systemic pattern of current code generation rather than a model-specific flaw (p. 9).

The second move addresses RQ4. Models with higher pass rates do not have fewer issues per passing task: Claude Sonnet 4 passes most tests but has 2.11 issues per passing task, while OpenCoder-8B passes the fewest and has 1.45 (p. 8). A case study of Claude 3.7 Sonnet versus Claude Sonnet 4 adds that the share of Blocker bugs nearly doubled while the pass rate rose (p. 19). From this the paper concludes there is no correlation between functional performance and code quality, and that benchmark scores are not a good indicator of overall quality and security (p. 1, p. 21).

The third move explains the defects. For each sub-category of smell, bug and vulnerability, the paper proposes a "potential contributing factor", mostly that the task needs non-local analysis (project-wide references, taint tracking from source to sink, resource lifecycles) that a context-limited, token-by-token generator does not do (pp. 11–15). It adds that vulnerabilities such as hard-coded credentials, weak cryptography and XXE are consistent across models, which it takes to point to training data containing insecure or outdated code as the most plausible origin (p. 15, p. 16). These explanations are hedged ("may", "possibly") and are not tested.

The paper closes by arguing for static analysis (SAST), expert human review and CI/CD integration as safeguards, and for Software Composition Analysis (SCA) to cover deprecated APIs and dependencies with known CVEs, which static analysis of the generated code alone does not address (p. 12, p. 16, p. 20, p. 21). It says prompt engineering is useful but not sufficient on its own (p. 16).

### Interlocutors

- Chen et al. 2021 (Codex / HumanEval): the source of the functional-correctness evaluation (Pass@1) that the paper says dominates assessment of LLM code; counterpoint (p. 3, p. 26).
- Dora et al. 2025 ("hidden risks of LLM-generated web application code"): cited for the finding that programmers using AI assistants can write less secure code with greater confidence, and for vulnerabilities across models; supporting prior work (p. 3, p. 15, p. 26).
- Cassano et al. 2023 (MultiPL-E) and Feng et al. 2024 (ComplexCodeEval): the benchmark datasets of the 4,442 tasks; data source (p. 5, p. 27).
- MITRE CWE and OWASP Top 10: reference taxonomies for the headline vulnerability classes (CWE-798, CWE-22, CWE-611); framing (p. 21, p. 26).
- Huang et al. 2025 (OpenCoder): the small open model included to test whether issues persist regardless of model size; data source (p. 5).

### Methodology

An empirical benchmark study. Each model generates Java solutions for all tasks with identical prompts and temperature zero; the generated files are scanned by SonarQube Cloud with the default ruleset; functional performance is measured as Pass@1 against the provided test suites (p. 5). Sonar rules are grouped by the authors into sub-categories (Appendix, pp. 23–25), and the "potential contributing factors" are the authors' interpretation, not measured.

### Empirical base

- 4,442 Java problems from MultiPL-E-mbpp-java, MultiPL-E-humaneval-java and ComplexCodeEval (p. 5).
- Five models: Claude Sonnet 4, Claude 3.7 Sonnet, GPT-4o, Llama 3.2 90B, OpenCoder-8B (p. 5).
- Test pass rates come only from the two MultiPL-E benchmarks; static analysis covers all three sources (p. 5).

### Findings

- Every model produced bugs, vulnerabilities and code smells; none produced consistently defect-free code (p. 9, p. 21).
- Issue density ranged from 19.48 (Claude Sonnet 4) to 32.45 (OpenCoder-8B) issues per KLOC (p. 8).
- The type mix was similar across models (p. 9).
- Vulnerabilities were mostly Blocker or Critical: over 70% Blocker for Llama 3.2 90B, and nearly two-thirds for OpenCoder-8B and GPT-4o (p. 10).
- The leading vulnerability classes were path traversal and injection, hard-coded credentials, and cryptography misconfiguration (p. 15).
- Hard-coded credentials (java:S6437) appeared in code from all five models (p. 17).
- Pass rate and issues per passing task did not move together (p. 8, p. 19).

### What the source offers

- A cross-model profile of SonarQube issue types, severities and sub-categories for LLM-generated Java, with rule-to-category mappings (pp. 9–16, pp. 23–25).
- A concrete counter-example to using a functional pass rate as a proxy for code quality and security (p. 8, p. 19).
- A set of model-specific rule counts (java:S2095, S6437, S3776, S2094) that illustrate the shared weaknesses (pp. 17–18).

### Stated gaps and limitations

The paper does not list limitations as such. It lists future work: prompt engineering and fine-tuning as mitigations, longitudinal studies of technical debt, LLM-driven refactoring of static-analysis findings, other languages, and architectures that address these weaknesses (p. 21). It frames the explanations as possible rather than established (pp. 11–15).

### Key claims

- On 4,442 Java tasks, all five LLMs tested produced bugs, vulnerabilities and code smells (p. 9, p. 21).
- The type distribution was similar across the models, about 90-93% code smells, 5-8% bugs and around 2% vulnerabilities (p. 9).
- The study found no direct correlation between Pass@1 on unit tests and the number of SonarQube issues in solutions that passed (p. 1).
- Claude Sonnet 4 had the highest pass rate (77.04%) and 2.11 issues per passing task; OpenCoder-8B had the lowest pass rate (60.43%) and 1.45 (p. 8).
- Between Claude 3.7 Sonnet and Claude Sonnet 4, the share of Blocker bugs rose from 7.1% to 13.71% while the pass rate rose from 72.46% to 77.04% (p. 19).
- Across all models, a large share of detected vulnerabilities was Blocker or Critical (p. 10).
- Hard-coded credentials, path traversal and injection, and cryptography misconfiguration were among the vulnerability classes seen across models (p. 15, p. 17).
- The consistency of vulnerabilities across models points to training data as the most plausible origin, according to the authors (p. 16).
- Prompt engineering is not a sufficient safeguard on its own; static analysis and expert human review are essential (p. 16).
- Static analysis should be complemented by Software Composition Analysis for deprecated APIs and vulnerable dependencies (p. 12, p. 21).

- Bug severity (Table 6, p. 9): GPT-4o 74.63% Major; Claude Sonnet 4 13.71% and Llama 3.2 90B 13.82% Blocker; OpenCoder-8B 12.05% Critical.
- Dead, unused or redundant code was 14.83% of Claude Sonnet 4's smells and 42.74% of OpenCoder-8B's (Table 9, p. 11).
- Control-flow mistakes were 48.15% of GPT-4o's bugs (Table 10, p. 13).
- Vulnerability sub-categories (Table 11, p. 15): hard-coded credentials 29.85% of OpenCoder-8B's and 23.58% of Llama 3.2 90B's; path traversal and injection 26.83-34.04% across models.
- Rule counts (pp. 17–18): java:S2095 (unclosed resources) 54 for Claude Sonnet 4, 25 for GPT-4o, 50 for Llama 3.2 90B; java:S6437 (hard-coded password) 20, 20 and 29 for the same models; java:S3776 (cognitive complexity) 422 for Claude 3.7 Sonnet, 112 for GPT-4o; java:S2094 (empty class) 531 for GPT-4o, 661 for OpenCoder-8B.
- Operational definitions: "Issues per Passing Task" normalises total issues against the number of functionally successful outputs (p. 8). Severity levels are SonarQube's Blocker, Critical, Major and Minor (p. 9).
- Reported gaps and inconsistencies: pass rates come from the two MultiPL-E benchmarks only, while issue totals cover all 4,442 tasks (p. 5, p. 7), and the paper does not say how issues in non-passing or untested outputs enter "issues per passing task". The abstract says the issues were counted "in benchmark solutions that passed the functional tests" (p. 1), while Table 2 uses total issues over all tasks (p. 8). No correlation statistic is reported for the "no correlation" claim, which the abstract words as "no direct correlation" (p. 1) and the conclusion as "no correlation" (p. 21). Section 7 says "67 distinct types of vulnerabilities" were identified (p. 15), and Table 4 gives 67 as OpenCoder-8B's total vulnerabilities (p. 9). A text note on p. 17 retains a draft marker, "[add ref?]".
