# CLAUDE.md — operating contract for the vault

This repository is a research knowledge base on **automated red teaming and vulnerability detection
for AI-generated software**, maintained by several contributors. It feeds two deliverables: a paper
(how insecure AI-generated code is; the methods and benchmarks for detecting its vulnerabilities and
red-teaming it; compliance with secure-coding standards) and a product that automatically detects
vulnerabilities and checks compliance in AI-generated code. This file defines how you work here.
These are not suggestions.

## 1. The dividing line

The default is: **you take care of what the source says; the contributors take care of what it
means.**

"What the source says" is the whole text, not just the parts that tabulate well. It includes the
argument — the thesis, the moves that lead to it, the concepts it mobilises, the authors it argues
with. Reporting that is your job, and reporting it well takes prose, not a list of fields. A
summary that records N and method but doesn't let a reader know **what the text maintains** is
incomplete, not safe.

The preserved default is about **not interpreting**, never about **being brief**. Extraction and
reporting (metadata, argument attributed to the source, key claims, bibliographic lineage,
structured facts, anchored quotes, format conversion, tags, link curation) are your job by default.

Interpretation, connection and synthesis **you do not produce on your own initiative**.
Specifically, you do not fill these sections without an explicit request:

- `## Reading`
- `## Connections`
- `## Disagreements`

This is a *default*, not a prohibition. If a contributor asks for a reading, a list of connections
or a synthesis, do it — well and without hedging. What must not happen is doing it in passing, in
the middle of an extraction task, without anyone asking. Cognitive debt may only be taken on
deliberately.

When you write in one of these sections on request, write under the subheading `### claude`, so
it stays distinguishable from the contributors' reasoning later.

The layer above the sources follows the same line:

- **Debate notes** map who holds which position, on what evidence, with anchors. That mapping is
  attributed reporting and is your job. *Choosing* what counts as a debate is selection: you
  propose debates, a contributor approves them, and you never create one unilaterally.
- **Positions documents** are synthesis. You write one only on request, under the direction a
  contributor gave, and you keep to that direction.
- Saying which side of a debate is right is interpretation, in either layer.

## 2. Folder contract

| Folder | Content | Who authors |
|---|---|---|
| `notes/00-questions/` | one hub per research question | everyone |
| `notes/10-debates/` | one note per contested question in the literature | you, after approval (§1); `## Reading` the contributors' |
| `notes/20-sources/` | one note per source | descriptive layer yours; interpretive layer the contributors' |
| `notes/30-positions/` | directed summaries of the literature's positions | you, on request; `## Reading` the contributors' |
| `notes/90-meta/` | audit, generated `matrix.md`, `candidate-debates.md`, templates | you (generated) — **except `taxonomy.md`**, which is human-declared (§4.9) |
| `references/annotations/` | contributors' readings, in their own voice | **contributors** — you only convert format and add tags |
| `references/pdfs/` | PDFs | intake |
| `references/web/` | markdown snapshots of web pages (evidence, versioned) | capture tooling |
| `data/` | extracted text, claims index (derived, regenerable) | scripts |
| `scripts/`, `docs/`, `tests/` | tooling and specification | you |

`references/annotations/` is read-only by default. You may convert a `.docx` or `.txt` to markdown,
add frontmatter and apply tags. You **do not rewrite their prose** — not to "improve" it, not to
shorten it, not to make the style uniform.

`notes/90-meta/matrix.md` (each source's stances across the debates, listed per source) is
generated by script from the `## Stances` lists of the debate notes. Nobody edits it by hand; to change it, change the debate note.

## 3. Frontmatter schemas

### Source note (`notes/20-sources/`)
```yaml
---
type: source
title:
authors: []
year:
venue:                 # journal, conference, publisher or outlet
source_type:           # peer-reviewed | preprint | book | report | press | blog | docs | data
interest:              # independent | vendor | undetermined
doi:                   # real DOIs only; a non-DOI link goes in url
url:                   # original URL (web source), https://arxiv.org/abs/<id> from a printed arXiv id, or repository without a DOI
pdf:                   # "[[references/pdfs/....pdf]]", empty until the PDF arrives
snapshot:              # "[[references/web/....md]]" (web source)
status: to-read        # to-read -> summarised -> read
summarised_by:         # model id that wrote the descriptive layer, e.g. claude-sonnet-5-5
reviewed_by:           # contributor handle; humans only
tags: []
---
```

Body, in this order:

1. `## Stated by the source` — the substantive body of the note, in subsections (see below).
   Everything attributed to the source itself, with a reporting verb ("the paper argues", "the
   author proposes"), never presented as assessment
2. `## Extracted facts` — the factual ballast of the argument (see below)
3. `## Quotes` — 5–8 passages that carry the argument (up to 12 for a long paper), verbatim, with a
   verifiable anchor (see §4)
4. `## Reading` — one `### <handle>` subheading per contributor, plus `### claude` when requested
5. `## Connections`
6. `## Disagreements`

#### The subsections of `## Stated by the source`

| Subsection | Content | Length |
|---|---|---|
| `### What it is about` | object, scope, intended audience, the question it pursues | 3–5 sentences |
| `### Argument` | **prose, not bullets**: the line of reasoning in the order the source builds it — premise, moves, conclusion; the concepts it coins or mobilises and what each does in the argument | 3–6 paragraphs |
| `### Interlocutors` | 4–5 central works (not a bibliography): author-year, what the source takes from each, and its role — foundation · target of critique · data source · counterpoint | 4–5 items |
| `### Methodology` | how the source supports what it claims. Non-empirical source: **name the mode of argument** (essay, narrative review, consulting framework, practice report) instead of listing what is missing | 1–2 paragraphs |
| `### Empirical base` | data, N, population, period — only when they exist | short |
| `### Findings` / `### Theses` | results, for an empirical source; the propositions the text lands on, for the others | bullets |
| `### What the source offers` | the material it provides to a researcher: an operational definition, a dataset, a framework, a counter-case, a citable number | 2–4 bullets |
| `### Stated gaps and limitations` | what the source itself acknowledges | short |
| `### Key claims` | the source's central claims, one line each, anchored (see below) | 3–6 bullets |

Target length of `## Stated by the source`, by the size and density of the source, not by medium:

| Source | Target |
|---|---|
| long paper or report (above ~8k words) | 800–1500 words |
| medium, argumentative text (thesis post, short working paper, ~1.5–5k words) | 600–1200 |
| short note, press item, docs page, dashboard | 300–600 |

`## Extracted facts` is counted separately: its size is that of what the source actually reports —
a paper with three tables yields more ballast than an essay, and that is not excess. Practical
ceiling for the whole note: **half** the source text. Past that, you are transcribing, not
reporting. Falling far below the floor almost always means you read the abstract and the tables,
not the text.

`### What the source offers` is the one place where the line slides — selecting is choosing. It is
bounded like this: it describes **what the source provides**, never whether it is right, whether
the evidence is strong, or whether it is worth more than another. That remains the contributors'.

A note with no PDF or snapshot has no material for `### Argument`, `### Interlocutors` or
`### Key claims`. It stays a skeleton until the primary source arrives — that is expected, not a
debt to fill by deduction.

#### `### Key claims`

The claims are what the corpus-level work reads: a script collects them into a claims index, and
debates are mapped from that index instead of from the full notes. So each claim has to stand on
its own:

- one line, one claim, with its anchor: `- On the study's benchmark, the detector's recall fell for
  vulnerability classes outside those it was tuned on (p. 4)` (a format example, not a real source;
  written on one line in the note, §6.2);
- the source's own **modality** — "suggests" stays "suggests", "may" stays "may";
- the source's own **scope** — population, task, setting, period — when the claim depends on it;
- the claims the source actually makes, not the ones a reader would draw from it.

Write them in the same pass as the rest of the note, while the full text is in context. Never
derive them from the abstract alone.

#### `## Extracted facts`

It is the factual ballast of the argument: numbers, operational definitions, what exactly was
measured, population, period, instrument. It is not an audit of absences.

Absence is still data, but concentrated in **one final block** and only when it matters to a claim
the source actually makes. "Opinion post does not report N" is not a finding — it is the genre.
"Claims a 55% speed-up without stating the task or the sample" is.

When the source contradicts itself — two counts of the same sample, a date given two ways, a
citation missing from its reference list — record both versions, attributed and anchored, and
leave them unresolved.

**`source_type` and `interest`** are largely factual — which outlet published it, and whether the
publisher sells what was measured. You **may** fill them when the relation is objective and evident
(arXiv → `preprint`; GitHub on Copilot → `vendor`), and leave them `undetermined` / empty in any
doubtful case. This matters more here than in most fields: much of the evidence on the security of
AI-generated code is published by the companies that sell what is measured — the models, the
coding assistants or the security scanners. A study by such a company about its own kind of
product is `vendor`; an academic benchmark that evaluates vendors' models is `independent`
(D38). Filling these fields does
**not** contradict the rule that judgement is human: `#evidence/` remains the contributors' alone.
`source_type` mirrors the `#source/` facet.

### Debate note (`notes/10-debates/`)
```yaml
---
type: debate
question:              # the contested question, one sentence
sources: []            # [[source notes]] with a stance in this debate
written_by:            # model id or contributor handle
reviewed_by:           # contributor handle; humans only
tags: []
---
```

Body, in this order:

1. `## Question` — what is contested, and the scope within which it is contested
2. `## Positions` — one `### <position>` per position, in prose: who holds it, on what evidence,
   with anchors. Attributed throughout; no position is presented as the correct one
3. `## Why they differ` — what separates the positions as the sources themselves present it:
   method, population, what was measured, period, interest of the publisher
4. `## Stances` — one line per source, in the fixed form the matrix script reads:
   `- [[source note]] · <position> · supports | contests | qualifies · (p. N)`
5. `## Reading`

A debate exists only with **at least three sources** taking a stance in it. Fewer than that is a
claim, not a debate, and stays in the source notes. A question that mapping finds contested but
short of three sources goes to `notes/90-meta/candidate-debates.md` — the question, the sources so
far with anchored claims, what it would need to become a debate. Candidates stay out of the matrix;
one becomes a debate only through a normal proposal.

### Positions document (`notes/30-positions/`)
```yaml
---
type: positions
direction:             # the contributor's brief, verbatim
lens:                  # by-debate | by-era | by-stakeholder | ... as the brief asks
question:              # "[[question hub]]", when it serves one
debates: []            # [[debate notes]] it draws on
written_by:
reviewed_by:
tags: []
---
```

Body, in this order:

1. `## Direction` — the brief, verbatim, so the document can be regenerated or updated against the
   same brief
2. `## Positions` — the summary itself, organised by the requested lens, every position attributed
   and anchored through its debate or source note
3. `## Gaps` — what the corpus does not cover for this brief
4. `## Reading`

### Question hub (`notes/00-questions/`)
```yaml
---
type: question
question:              # the research question this hub organises
written_by:
reviewed_by:
---
```

Body: `## Question`, `## Debates` (index of debate notes), `## Positions` (links to positions
documents), `## Open`.

### Annotation (`references/annotations/`)
```yaml
---
type: annotation
written_by:            # contributor handle
about:                 # "[[source note]]"
reviewed_by:
---
```

## 4. Hard rules

These have no exception, not even on request:

1. **Never invent** a quote, DOI, page number, author or year. If you don't know, leave it empty and
   say so.
2. Every claim attributed to a source carries a **verifiable anchor**: `(p. N)` for a PDF; `(¶ N)`
   or `(§ section name)` against the snapshot in `references/web/` for a web source. Never a loose
   claim. In `(p. N)`, N is the **physical** page of the PDF (1 = first page of the file) — the
   `<!-- page N -->` marker in `data/extracted/`, not the number printed on the page. A claim drawn
   from several pages lists them in one anchor: `(p. 3, p. 8)` or `(pp. 10–12)`. A quote stays on
   one page.
3. Before proposing a debate, **search the existing debates** — including under different wording.
   A debate needs at least three sources (§3).
4. When merging debates, **preserve the prose and authorship of both sides**. Never rewrite
   someone's text into your voice. A merge is attributed juxtaposition, not paraphrase.
5. Everything you write records the model id that wrote it — `summarised_by` on a source note,
   `written_by` elsewhere — **including when written on request**.
6. `reviewed_by` is filled only by a human. You never assign yourself a review. You may move
   `status` from `to-read` to `summarised` when you have written the descriptive layer — that
   records a mechanical fact — but never to `read`, even when the note is obviously complete.
7. No operation of yours overwrites the interpretive layer of an existing note. When in doubt,
   append and flag; do not replace.
8. Fabrication is checked, not trusted. A note written by a lighter model, or summarised in a long
   batch, is not finished until its quotes and anchors have been checked against the source text.
9. **`notes/90-meta/taxonomy.md` is human-declared.** Only contributors create new tags. You
   **propose them in conversation**; editing the file is theirs. This holds even when the tag is
   obviously needed, even in the middle of an operation they already approved, and even on
   request — if asked, write the line in the conversation for them to paste. Applying a tag that
   already exists is another matter, and remains your job (§7).
10. **A claim never comes out stronger than its source.** Dropping a hedge, widening the scope or
    turning a correlation into an effect is misreporting. This holds for key claims, for the
    positions in a debate, and for every summary of a debate in a positions document.

## 5. Language

Notes, tags, filenames and frontmatter in **English**, unless a contributor explicitly states
otherwise for a given piece of work. Verbatim quotes stay in the source's original language —
translate below, if useful, marked as a translation.

## 6. Note form

A note that cannot be read at a glance is not ready. This applies to everything inside `notes/` and
`references/` — what Obsidian renders. `CLAUDE.md`, `docs/` and `README.md` are read in an editor,
stay outside this, and keep the 100-column wrap.

### Line breaks

1. **A paragraph is one line.** Never wrap prose at a fixed column. Obsidian renders a single line
   break as a visible break: a paragraph wrapped at 100 columns looks ragged when read. Let the
   software reflow.
2. **A list item is one line**, with no indented continuation. A sub-item takes two spaces and its
   own `-`.
3. **Never leave trailing whitespace.** Two trailing spaces are a forced break in markdown —
   invisible in the editor and visible when read.

### Spacing

4. Exactly **one** blank line between blocks: between paragraphs, and before and after a heading,
   list or quote. Never two, never none.
5. The file ends with a newline and nothing else.
6. **A section with no content stays empty** — just the heading. Don't write "N/A", "not
   applicable" or a dash: the emptiness is what the audit counts.

### Structure

7. `##` only for the schema's sections (§3), in schema order; `###` for subsections. Don't invent a
   `##`-level section and don't skip a level.
8. Bullets always with `-`. Numbered list only when order matters.
9. No horizontal rule (`---`) in the body — it collides with the frontmatter delimiter. No HTML, no
   emoji.

### Emphasis

10. **Bold** marks the term the note introduces or the number that supports the claim — one or two
    per paragraph. Bold in every bullet sentence highlights nothing; it only makes the page heavy.

### Quotes

11. One quote per bullet, on one line, in quotation marks, with the anchor after the quotes:
    `- "..." (¶ 14)`. A translation comes after the block, labelled `Translation (¶ N):`.

### Frontmatter

12. Fields in template order. Don't fight Obsidian's YAML normalisation — it rewrites quotes and
    list indentation on save, and that is not an error. What matters is the field and the value.

## 7. Tags

**Controlled** vocabulary in `notes/90-meta/taxonomy.md`. Check it before applying any tag.

Facets: `#topic/`, `#method/`, `#source/`, `#evidence/`, `#state/`.

Two different operations, with different owners — what follows is the distinction rule §4.9
protects:

**Applying** a tag that already exists in the taxonomy to a note: your job, in the factual facets —
`#topic/`, `#method/`, `#source/`. `#evidence/` belongs to the contributors: it is judgement, not
extraction. The `interest:` field goes with `#source/` and you fill it when the relation is evident.

**Declaring** a new tag, by writing it in `taxonomy.md`: theirs. If you need a tag in any facet that
doesn't exist, write the proposed line in the conversation — in the file's format, ready to paste —
and carry on without it. A note that would need that tag stays without it until someone applies
it; that is the correct behaviour, not a pending item to resolve on your own.

## 8. Role after reading

When a contributor writes `## Reading`, your job becomes **interlocutor**: point out tension with
other notes, counterexamples already in the vault, claims without strong evidence, terms being used
in two different ways. The same applies when a contributor brings an idea to brainstorm or
stress-test: look for the strongest objection, not the most comfortable agreement. Contesting is
useful; agreeing out of politeness is not.

## 9. Skills

| Skill | When to use |
|---|---|
| `new-source` | a PDF **or a URL** — paper, post, report — to summarise; routes to the right path |
| `summarise-pdf` | the PDF path in isolation, to run with a clean context; writes key claims too |
| `summarise-web` | the URL path in isolation: captures a snapshot, then summarises it; writes key claims too |
| `extract-claims` | backfill `### Key claims` in source notes written without them |
| `map-debates` | assign new claims to existing debates, propose new debates and updates, flag duplicates |
| `refresh` | after a batch of sources or a merge: backfill missing claims, then run `map-debates` |
| `positions` | a directed summary of the literature's positions, from a contributor's brief |
| `review-links` | audit the web of links and tags — especially after a merge |
| `audit` | see the state of the reading debt |
| `stress-test` | contest a reading already written, or an idea brought for testing |

All of them **propose before applying**. None creates, merges or deletes a file without
confirmation. In particular:

- `map-debates` stops after proposing; nothing is written until a contributor approves.
- `refresh` reports how many sources are missing claims and asks before launching agents, then
  stops at `map-debates`' approval step.
- `positions` restates the brief before writing — topics in and out, lens, the debates and sources
  in scope — and writes only after the contributor confirms that reading.

## 10. Agents

Summarising, checking and mapping run in subagents defined in `.claude/agents/`, so each job gets a
clean context and the model choice lives in the repository rather than in the session.

| Tier | Model | Work |
|---|---|---|
| summary | Sonnet | full source notes, key claims included; key-claims backfill |
| light | Haiku | fact-checking quotes and anchors; short, low-argument sources |
| judgement | Opus | `map-debates`, `positions` |
| main session | session model | stress-testing, brainstorming, anything a contributor drives directly |

One source per summary agent; the agent returns a short report, not the note. Agents are bound by
this contract exactly as the main session is — the hard rules (§4) do not loosen for a cheaper
model, and rule §4.8 exists because of it.

### Token economy

The skills are built to these principles:

1. Agents read the text extracted from a PDF (`data/extracted/`), never the PDF itself.
2. Key claims are written in the same pass as the summary; a source is never re-read for them.
3. Corpus-level skills read the script-generated claims index (claim · source · anchor), not the
   notes, and open a note only to check a specific point.
4. Mapping is incremental: the script hands `map-debates` only the claims not yet in any debate,
   plus a one-line index of the existing debates.
5. `refresh` runs after a batch of sources, not after each one.
6. Deterministic work stays in scripts and costs no model tokens: extraction, quote checking, the
   claims index, the matrix, the pool of unassigned claims, the audit.
7. A source whose extracted text has not changed is not summarised again.
8. `positions` reads debates, the matrix and claims first, and opens source notes only for what the
   brief needs.

## 11. Collaboration

Each contributor works on their own branch; `main` is the consolidated state. After each merge, run
`/review-links` and `/refresh`: a git merge resolves text, it does not resolve two debates asking
the same question under different wording — `map-debates` flags those for merging (§4.4).
